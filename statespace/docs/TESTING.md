# Testing

Four dependency-free tools, all built by the normal CMake build alongside
the plugin (`build/bin/dsp_regression`, `build/bin/audio_testbench`,
`build/bin/fit_gain_curve`, `build/bin/fit_multiband_compressor`) -- none
link against DPF/DGL, they only use the framework-independent code in
`plugin/dsp/`. The first two are pass/fail verification; the other two are
offline trainers -- for the single-band nonlinear gain stage and the
multiband one, respectively (see `docs/ARCHITECTURE.md`'s
"NonlinearSchedule" and "MultibandSchedule" sections).

## `dsp_regression` -- fast, pure-math checks

```sh
./build/bin/dsp_regression
```

Runs in well under a second: identity passthrough is bit-exact, a
deliberately unstable matrix gets clamped and stays finite under sustained
full-scale input, an RBJ lowpass reproduces the expected magnitude shape,
JSON presets round-trip exactly, `normalizeToUnityPassbandGain()` hits
exactly 0 dB, a cascaded band-limit filter has the right shape, (test
`[7]`, added after a real bug -- see below) a narrow notch filter actually
notches, (test `[8]`) a hand-set `NonlinearSchedule` curve settles to
exactly the closed-form compressor gain formula predicts and stays
transparent below threshold, (test `[9]`) `GainCurveTrainer::fit()`
round-trips a known synthetic schedule -- fit against audio generated by
that same schedule -- recovering attack/release exactly and the curve to
within a fraction of a dB, and (test `[10]`) the sibling EQ plugin's
`EqModel::assembleStateSpace()` (dense state-space matrix, what the audio
engine actually runs) and `evaluateCombinedResponse()` (closed-form
product of each band's own biquad response, what the EQ's GUI actually
draws every frame -- see `docs/ARCHITECTURE.md`'s "EqModel / EQ plugin"
section for why it needs a second, cheaper code path at all) agree to
numerical precision, as they must for the same LTI system, (test `[11]`)
`SpectrumAnalyzer` (the EQ graph's background spectrum, see
"SpectrumAnalyzer" in `docs/ARCHITECTURE.md`) reads a handful of pure
tones at known frequencies/levels back to essentially exact level (worst
case ~0.002dB in practice) and the correct log-spaced band, (test `[12]`)
a same-order `StateSpaceEngine` model swap glides smoothly toward the new
target on a closed-form one-pole trajectory (checked to within `1e-6`)
instead of switching instantly, and (test `[13]`) an order-changing swap
between two *same-gain* models -- so an un-ducked instant switch would
look identical at every sample except during the transition itself --
visibly dips to silence and recovers, confirming the duck described in
`docs/ARCHITECTURE.md`'s "Real-time engine" section actually runs,
(test `[14]`) the mono EQ plugin's whole DSP path -- see below,
(tests `[15]`-`[17]`) the multiband compressor mechanism -- see below, and
(test `[18]`) the multiband compressor *plugin*'s own coefficient-mapper
layer (`MbCompressorModel::assembleStateSpace()` vs its closed-form
`evaluateCombinedResponse()`, a JSON round-trip, and the
`addCrossover()`/`removeCrossover()` band-count invariant) -- the same
cross-check pattern as test `[10]`'s identical one for `EqModel`.
Exits non-zero if anything fails.

### Test `[14]` -- the mono EQ's equivalence and its actual saving

The mono EQ plugin (`plugin_eq_mono/`) exists purely to cost less than the
stereo one, so its test asserts both halves of that claim:

- **It really is equivalent.** The same band list, assembled via
  `eq::assembleMonoStateSpace()` and run through `MonoStateSpaceEngine`,
  must produce **sample-for-sample** what the stereo `StateSpaceEngine`
  produces on one channel (measured: exactly `0.0` difference). They
  describe the same LTI system by construction, so any discrepancy at all
  means the mono realization or the SISO cascade packing is wrong -- and
  this is an end-to-end check (assembler + guard + engine + recursion),
  not just a comparison of matrix shapes.
- **It really is cheaper.** The mono assembly must be *exactly half* the
  stereo assembly's order for the same bands. That halving is the entire
  mechanism behind the plugin's lower CPU cost (see
  `plugin/dsp/MonoStateSpaceTypes.hpp`), so if it ever regressed to
  stereo-sized the plugin would still work perfectly while silently
  ceasing to be worth having -- which nothing else here would catch.
- `MonoStabilityGuard` must also agree with `StabilityGuard` on the narrow
  50Hz/Q=25 filter from test `[7]`, checked against the stereo guard's own
  result rather than a hard-coded number, so the two stay in sync.

Note this file's tools exercise the *shared DSP core* (`plugin/dsp/`),
which all three plugins are built from -- there is currently no
`audio_testbench`-style WAV-file exerciser specifically for either EQ
plugin's own factory presets (neither ships any yet), since `EqModel`
assembles into an ordinary `StateSpaceMatrices` that the existing tools
already cover once assembled.

### Tests `[15]`-`[17]` -- the multiband compressor mechanism

See `docs/ARCHITECTURE.md`'s "MultibandSchedule" section for the full
mechanism these pin down:

- **`[15b]`**: the same flatness at every crossover slope the plugin offers (order 2/4/6/8 = 12/24/36/48 dB/oct), plus each low
  band being -6.02dB at its crossover. Pins down the fix for a real bug: the LR stages used to be identical Q=0.707 sections (right only
  at order 4), leaving a -40dB/-58dB hole at 12/36 dB/oct and a -6dB dip at 48. Now each order uses its own Butterworth-N-squared Q table,
  and the odd-N orders (2, 6) invert the high-pass side so LP and HP sum flat.
- **`[15]`**: `mappers::makeStereoCrossoverBank()`'s Linkwitz-Riley
  crossover sums to within 0.2dB of exactly flat (0dB) across a 20Hz-15kHz
  sweep when every band's own gain is 0dB, and its `BandSplit` bookkeeping
  (`stateStart`/`stateCount`/`feedD`) exactly partitions the assembled
  order with each band's `feedD` summing to the assembled matrix's own
  `D` -- the two properties `StateSpaceEngine`'s multiband branch depends
  on for correctness.
- **`[16]`**: mirrors test `[8]`, per band -- two bands with different
  hand-set threshold/ratio, checked simultaneously against the closed-form
  compressor formula. Band 0 (a lowpass band, passes DC) is checked with
  sustained DC input, exact and ripple-free just like test `[8]`; band 1
  (includes a highpass, blocks DC) is checked with a sustained tone well
  above the crossover, measured via settled RMS level.
- **`[17]`**: mirrors test `[9]` -- `GainCurveTrainer::fitMultiband()`
  recovers two different known per-band curves from one synthetic
  (full-mix input, full-mix target) audio pair. This test is also what
  found the phase-alignment bug described in `docs/ARCHITECTURE.md` and
  `docs/EXTENDING.md`'s "Multiband compression" sections -- worth reading
  if this test ever regresses, since the failure mode (attack/release
  landing on the wrong grid point, several dB of curve error) looks like a
  fitting-quality problem before it's traced to a phase mismatch.

## `audio_testbench` -- real audio, real engine, cross-checked

```sh
./build/bin/audio_testbench
```

Works from any current directory, including `build/bin/` itself -- with no
arguments it defaults to this project's own `presets/factory/` and
`tools/testbench/output/` (their absolute paths are baked in at build time
via a CMake-injected `-D`, see `CMakeLists.txt`), regardless of where you
run it from. Pass explicit paths to point it at a different preset folder:
`./build/bin/audio_testbench /path/to/presets /path/to/output`.

For every `.ssjson` in the presets directory, this generates real test audio
(a 6-second logarithmic sine sweep 20 Hz-20 kHz, and a probe signal of
steady tones at ~25 frequencies, each held long enough for that specific
model's slowest expected settling time), runs it through the *actual*
`StateSpaceEngine` class the plugin itself uses -- not a reimplementation
-- and:

- measures each tone's steady-state gain and compares it against
  `TransferFunction::evaluate()` at that exact frequency, an independent
  frequency-domain computation (dense complex linear solve, no recursion)
  of the same underlying model. Close agreement (checked to within 0.5 dB)
  is strong evidence the model is being evaluated correctly end-to-end,
  since the two code paths have nothing in common except the coefficients
  they're both reading;
- checks a small per-preset table of "at this frequency, expect roughly
  this gain" (see `spotCheckTable()` in the source) -- a human-meaningful
  sanity check that the *design* matches intent, not just that the two
  computations agree with each other;
- for any preset with `nonlinear.enabled` (the state-dependent gain
  stage), **skips** the transfer-function cross-check above -- it's a pure
  LTI/frequency-domain computation that doesn't model the nonlinear stage
  at all, so a divergence there is expected, not a bug (`dsp_regression`
  tests `[8]`/`[9]` verify that stage's correctness directly instead) --
  and **adds** a different, dedicated check: since every probe tone is
  generated at the same fixed level, a state-dependent gain keyed off
  level should compress every one of them by the same amount regardless of
  frequency. The spread between the loudest- and quietest-measured probe
  must stay under 0.3 dB. This is a permanent regression guard for a real
  bug (see below);
- confirms the engine's output stays finite and bounded on the broadband
  sweep;
- writes every input and processed-output signal as a WAV file into the
  output directory (`_input_*.wav` once, `<preset>_sweep_out.wav` /
  `<preset>_tones_out.wav` per preset) so results can be listened to or
  inspected in an external tool (Audacity, a spectrum analyzer, ...), not
  just read as pass/fail numbers -- and a `report.txt` with the same text
  the tool prints to the console.

Exits non-zero if any check fails. The output directory is git-ignored
(regenerate by re-running the tool; nothing there is source).

## The bug this was built in response to

While adding a 50 Hz hum-removal notch preset, loading it produced no
visible dip in the Bode plot and no audible effect -- "difficult to say if
it's working." Investigating found a real, fairly serious bug in
`StabilityGuard`: its spectral-radius estimate (a single-vector power
iteration) was measurably biased for a complex-conjugate dominant pole
pair of *exactly* equal magnitude -- the routine case for any resonant
biquad, not an edge case -- and its refinement loop checked convergence
against the loose exact norm bound instead of that (biased) estimate,
which for the matrix shape every biquad mapper produces can be
structurally ~3x the true spectral radius and so never actually converges.
Together, these silently collapsed the notch filter's coefficients to
~30% of their designed value, turning a filter that should have had a
sharp, audible dip into something almost indistinguishable from a flat
passthrough.

The fix (see `plugin/dsp/StabilityGuard.cpp` for the full explanation):
replaced the power-iteration estimate with one based on repeated squaring
of the matrix (`rho(A) = lim ||A^N||^(1/N)` for any submultiplicative
norm, which holds unconditionally -- no dominant-eigenvalue-gap assumption
needed), fixed the refinement loop to check convergence against that
(now-accurate) estimate, and raised the default stability ceiling from
0.999 to 0.99995, since a narrow/high-Q filter's true pole radius routinely
sits in exactly that range by design and double-precision arithmetic makes
that an entirely safe margin. `dsp_regression`'s test `[7]` and
`audio_testbench`'s `notch_50hz_hum` case both pin this down permanently.

## `fit_gain_curve` -- learning a nonlinear gain curve from example audio

```sh
./build/bin/fit_gain_curve <base_preset.ssjson> <input.wav> <target_output.wav> <output_preset.ssjson>
```

Loads a base (LTI) preset, reads an example input WAV and the
corresponding desired-output WAV (same length/sample rate), and fits a
`NonlinearSchedule` (attack, release, and the 25-knot gain curve) via
`GainCurveTrainer::fit()` -- see `docs/ARCHITECTURE.md`'s
"NonlinearSchedule" section for how the fit itself works. Prints the fitted
attack/release, residual RMS error (dB), and a preview of the curve, then
writes a new preset (re-validated through `StabilityGuard::enforce()`)
with the learned `nonlinear` block. Verified end-to-end against a
simulated reference compressor (known threshold/ratio/attack/release/
makeup): recovered attack/release exactly and the curve to within
0.003-0.005 dB RMS. `presets/factory/trained_compressor_demo.ssjson` is a
real output of this tool, not a hand-authored curve.

## `fit_multiband_compressor` -- the same idea, N independent bands

```sh
./build/bin/fit_multiband_compressor "<crossover_hz_csv>" <input.wav> <target_output.wav> <output_preset.ssjson> [lr_order=4]
```

Same overall shape as `fit_gain_curve`, generalized: takes an ascending,
comma-separated list of crossover frequencies instead of a base preset
(there's no separate "base filter" here -- the Linkwitz-Riley crossover
bank itself, `mappers::makeStereoCrossoverBank()`, *is* the assembled
model's A/B/C/D) and fits one independent `NonlinearSchedule` per band via
`GainCurveTrainer::fitMultiband()` -- see `docs/ARCHITECTURE.md`'s
"MultibandSchedule" section for the mechanism, and for a real phase-
alignment bug found while building it (also covered by `dsp_regression`
test `[17]`, verified end-to-end here against real WAV files with the same
result). Refuses (rather than silently dropping bands) if the crossover
list would exceed `kMaxBands` (6). Prints each band's own fitted
attack/release/residual RMS, then writes a new preset -- an ordinary
`.ssjson`, loadable and hand-editable in the base plugin exactly like any
other, since a crossover bank is just another LTI mapper output.

## A second bug this caught: frequency-dependent envelope smoothing

While validating the trainer against real WAV files, a spot-check in
`audio_testbench` came back with an oddly frequency-dependent measured
gain for what should have been one consistent compression amount. The
envelope follower driving the nonlinear gain stage was smoothing in the
**dB domain**, applied to each sample's instantaneous `|signal|` --
which touches 0 (dB: -infinity) at every zero crossing of an AC signal,
twice per cycle. That made the same input *level* compress differently
depending on the signal's *frequency* (higher frequency = more zero
crossings per unit time = more frequent -infinity excursions dragging
the smoothed envelope down): measured gain varied by up to ~1.2 dB
between a 100 Hz and a 3 kHz tone at the identical input level -- real
compressors don't do this.

`dsp_regression`'s tests `[8]`/`[9]` didn't catch it because they test
against constant (DC-level) signals, which have no zero crossings. It
took a realistic sine-tone probe (exactly what `audio_testbench` runs) to
surface it. The fix: smooth the envelope in the **linear** amplitude
domain instead, converting to dB only at the point of curve lookup (see
`plugin/dsp/StateSpaceEngine.hpp` and `plugin/dsp/GainCurveTrainer.cpp`,
which must both do this identically). That brought the frequency spread
down to ~0.03-0.1 dB. `audio_testbench` now has a permanent regression
check for this (see above, "the spread ... must stay under 0.3 dB") on
every nonlinear-enabled preset.
